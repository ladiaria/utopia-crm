# Removal of the dead `Billing` model

- **Date:** 2026-10-27
- **Author:** Tanya Tree + Claude Opus 5.5
- **Ticket:** gl65-remove-billing
- **Type:** Refactor
- **Component:** Invoicing (models, views), fixtures
- **Impact:** Data model, extensions with a FK to `Billing`

## 🎯 Summary

`invoicing.Billing` modelled the "billing runs" of the days when invoices were generated by hand: each run had a
progress counter, a status, a list of excluded contacts, and grouped the invoices it created through
`Invoice.billing`. Billing has been daily for years and nothing creates or reads a `Billing` anymore (at la diaria,
the last run is from April 2021). The model, the FK on `Invoice`, the view that listed a run's invoices and its
template, the `BILLING_STATUS` choices and the "billing" permissions in the default groups fixture are removed. Found
by la diaria while auditing amount sums for multi-currency invoices (it/utopia-crm-ladiaria#65).

## ✨ Changes

### 1. The model and the FK on `Invoice`

**Files:** `invoicing/models.py`, `invoicing/choices.py`, `invoicing/migrations/0031_remove_billing.py`

`Billing` and `BILLING_STATUS` are deleted. `Invoice.billing` (nullable, `SET_NULL`) is removed from `Invoice` and
from `HistoricalInvoice`. The imports that only `Billing` used (`Q`, `User`, `Subscription`, `Contact`) go too.

### 2. The unreachable view and its template

**Files:** `invoicing/views.py`, `invoicing/templates/billing_invoices.html`

`billing_invoices` listed the invoices of a run. No URL routed to it, so it was already unreachable.

### 3. Permissions in the default groups fixture

**File:** `fixtures/default_groups.json`

`add_billing` and `change_billing` are removed from the two groups that had them. With the model gone, `loaddata`
would fail on them.

### 4. `invoicing/api.py` imports `Subscription` from `core.models`

**File:** `invoicing/api.py`

It imported `Subscription` from `.models`, which only worked because `invoicing/models.py` imported it for `Billing`.

## 📁 Files Modified

- **`invoicing/models.py`** — `Billing` and `Invoice.billing` removed, unused imports cleaned up.
- **`invoicing/choices.py`** — `BILLING_STATUS` removed.
- **`invoicing/views.py`** — `billing_invoices` removed.
- **`invoicing/api.py`** — `Subscription` imported from `core.models`.
- **`fixtures/default_groups.json`** — `add_billing` / `change_billing` permissions removed.

## 📁 Files Created

- **`invoicing/migrations/0031_remove_billing.py`** — Removes `billing` from `Invoice` and `HistoricalInvoice`, and
  deletes `Billing`.

## 📁 Files Deleted

- **`invoicing/templates/billing_invoices.html`** — Template of the removed view.

## 📚 Technical Details

**No invoice is deleted.** The FK was `SET_NULL`, and removing the field drops the column (`ALTER TABLE ... DROP
COLUMN`), not rows. In PostgreSQL that is a catalog change, fast even on a large `invoicing_invoice`.

**Extensions with a FK to `Billing`.** A customization package with a model pointing to `Billing` (la diaria had
`BillingExtension`, a `OneToOneField`) has to delete that model in its own migration, and that migration has to run
before `invoicing.0031_remove_billing`:

- **On an existing database**, migrating the package before the base is enough. Otherwise `DROP TABLE
  invoicing_billing` fails, because the extension's FK constraint depends on it.
- **On a new database** (a fresh install, a recreated test database), the order is not up to you: Django plans apps
  alphabetically, `invoicing` runs before most package names, and the package's old migration that creates the FK to
  `invoicing.Billing` fails because the model no longer exists in the migration state. The package's deletion
  migration needs a `run_before`:

```python
class Migration(migrations.Migration):
    dependencies = [("mypackage", "00XX_previous")]
    run_before = [("invoicing", "0031_remove_billing")]
    operations = [migrations.DeleteModel(name="BillingExtension")]
```

`run_before` points to a migration that must already exist, or Django raises `NodeNotFoundError`. So the package's
code that deletes the extension goes out first (and is migrated), then this change, and then the `run_before` in the
package.

## 🧪 Manual Testing

1. **Migration on an existing database:**
   - With any extension pointing to `Billing` already deleted, run `python manage.py migrate invoicing`.
   - **Verify:** `0031_remove_billing` applies, `invoicing_billing` no longer exists, and the invoice count is the same
     as before.

2. **Invoices still work:**
   - Open a contact's invoice list and the detail of an old invoice that had a billing run.
   - **Verify:** both pages load as before.

3. **Default groups fixture:**
   - On a test database, run `python manage.py loaddata default_groups`.
   - **Verify:** it loads without errors, and the Finances group no longer has `billing` permissions.

4. **Edge case — new database with an extension:**
   - With a customization package that still has its model pointing to `Billing` and no `run_before`, create a
     database from scratch (for example, run the tests without `--keepdb`).
   - **Verify:** migrating fails at the package's migration that creates the FK. With the `run_before`, it goes
     through.

## 📝 Deployment Notes

- **Migrations required:** `invoicing.0031_remove_billing`.
- If a customization package has a model with a FK to `Billing`, delete it and migrate the package **first**.
- Optional: `python manage.py remove_stale_contenttypes` removes the `billing` content type and the groups'
  orphan permissions.
